# Database mutation atomicity audit

Date: 2026-08-11  
Scope: runtime persistence code in `apps/backend/src` (services, event projectors, schedulers, and bootstrap seeding). Schema migrations are excluded: TypeORM executes each migration through its migration runner and they are deployment-time, not request-time, operations.

## Executive finding

The application has real integrity risks, concentrated in the original domain services rather than everywhere equally. The execution subsystem already demonstrates the desired direction: it uses a database transaction for lifecycle transitions and uses conditional updates/upserts for hot-path state changes. Most task, thread, context, tag/project, identity, OAuth, and configuration workflows instead perform a read, one or more writes, then a reload/event/external call with no common transaction boundary.

The primary failure modes are:

1. **Partial aggregates.** A parent row can be committed before its tags, relations, child rows, or companion record are written. A process crash or later validation error leaves a valid-looking but incomplete object.
2. **Lost updates.** `findOne` → mutate entity → `save` is used for mutable aggregates, even though many entities have `@VersionColumn`. TypeORM increments that column; it does not turn a plain `save` into compare-and-swap. No caller supplies an expected version and the update predicates do not check `row_version`.
3. **Check-then-act races.** Existence/count checks are used as authorization or uniqueness gates, then a separate write follows. Some database constraints catch the duplicate, but the service often does not translate it or atomically restore companions.
4. **Cross-service partial work.** Services call other services which use their own repositories, so wrapping only the outer `save` would not help. This is the strongest reason to introduce use-case/application services that own a transaction and pass an `EntityManager`/repository bundle downward.
5. **Commit versus side effect gap.** Events are emitted after persistence, which avoids sending events for a rolled-back change today, but a process can crash after commit and before emit. A future reliable design needs a transactional outbox plus idempotent consumers. External chat/OAuth calls must remain outside DB transactions and need a saga/compensation or retry model.

The audit found no universal requirement to put every `save` in a transaction. A single SQL statement is already atomic. The recommended default is: one use-case transaction per business invariant; conditional SQL or a uniqueness constraint for a simple compare-and-set/claim; and an outbox for durable post-commit effects.

## How to read the inventory

Verdicts:

- **Red — fix first:** security-sensitive, can double-spend/reuse a credential, loses a business invariant, or leaves a complex aggregate inconsistent.
- **Amber — transaction/CAS needed:** multi-step invariant or a user-visible lost-update window, but lower immediate blast radius.
- **Green — adequate:** one statement or an intentionally transactional workflow. “Green” does not mean the surrounding caller is necessarily safe.
- **Grey — bootstrap/legacy:** not request-path critical, but should become idempotent before multi-instance deployment.

“Event” means an in-process event after the write; it is not a durable outbox.

## Existing safeguards worth retaining

- Foreign keys and unique constraints prevent several bad states: actor slug, user email/actor, agent actor, active execution per task, task queue per task, tag name, project tag/slug, and mapping uniqueness.
- `McpRegistryService.createServer`, `ThreadsService.createThread`, `ThreadsService.attachTask`, `ThreadsService.addParticipant`, and `AgentsService.createAgent` translate or recover from some constraint races. Keep the constraints, but make the full aggregate atomic.
- `MetaService.incrementTagUsage` uses a correct atomic SQLite upsert.
- `ScheduledTasksService.claimDueTaskExecution`, execution heartbeat/session/stat/tool-count updates, and the active-execution lifecycle use conditional SQL/transactions. These are the implementation templates for the rest of the codebase.

## Target architecture and rules

1. Controllers/MCP handlers call one application **use case** per command. Use cases own validation order, transaction boundary, return result, and outbox records.
2. Domain services become focused collaborators that accept an `EntityManager`/repository port when called inside a use case; they must not silently open a second transaction.
3. Repositories own persistence mechanics: `insertIfAbsent`, `claim`, `updateIfVersion`, relation add/remove, and guarded delete. Application services should not assemble large mutable entity graphs.
4. Database constraints are the authority for uniqueness and referential integrity. Pre-checks improve error messages only; writes must translate constraint errors.
5. Use optimistic concurrency deliberately: API mutation DTOs carry `expectedRowVersion` for user-edited resources; SQL predicates include it and failures return a conflict. For append/counters/claims, use atomic expressions/conditional update instead.
6. In-process events are temporary. Add an outbox table written in the same transaction and a retrying dispatcher. Consumers must be idempotent using an event ID/deduplication key.
7. Never hold a DB transaction around network/LLM/OAuth work. Persist an intent/state, commit, call externally, then apply an idempotent result transition; use compensation only where required.

## Verification needed before changing production semantics

- Establish a SQLite concurrency test harness with two independent `DataSource` instances against the same temporary DB and WAL/busy-timeout settings matching production.
- For each red operation, inject failure after every write and assert rollback/no externally visible partial aggregate.
- Race two requests for: task/context/thread create, tag create/association/removal, agent/user create, client registration, OAuth code exchange, refresh rotation, schedule claim, and JWKS rotation.
- Audit current data before adding constraints: duplicate active chat providers, duplicate connection names per server, orphan tags (including thread/blueprint references), orphan actor/user/agent pairs, and incomplete OAuth journeys.
